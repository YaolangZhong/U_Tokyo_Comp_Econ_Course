\begin{frame}{Three Cases}
\begin{itemize}
\item \courseexample{Case: Keep earlier versions}\\
You keep revising a file but worry that saving your latest edits will erase useful earlier work. Soon you have \texttt{v1}, \texttt{v2}, \texttt{v3}, \ldots\ What changed, and which version should you use?\\
\textbf{With Git:} record versions in one project and revisit earlier work.
\medskip
\item \courseexample{Case: Work with others}\\
You and a partner edit the same project. You exchange files and explain each change in messages or meetings, then try to combine your edits without losing either person's work.\\
\textbf{With Git:} compare changes, see who made them, and merge contributions.
\medskip
\item \courseexample{Case: Build on an existing project}\\
You find a useful project online and want to try it or adapt it. After downloading a copy, its author releases improvements. How do you bring those updates into your own copy?\\
\textbf{With Git:} clone the repository and fetch later updates to integrate.
\end{itemize}
\end{frame}

\begin{frame}{Git: Keep Earlier Versions}
\term{Git} is software you install on your computer to keep a history of your work. It helps you record versions, revisit earlier work, and combine changes.
\par\medskip
\begin{itemize}
\item Start with an ordinary working folder containing your files. \term{Initialize} Git with \texttt{git init}: the folder becomes a \term{repository}, a project whose history Git can record.
\item A \term{commit} is like a snapshot of the project's recorded files at a particular point. You can return to that version or recover useful content from it.
\item Each commit has a \term{hash}: an identifier made of letters and numbers, often displayed in a short form such as \texttt{a3f7c2d}. You also write a message, such as ``Add a plotting function.''
\item Git keeps these snapshots in its history, so you can keep working in one folder instead of making \texttt{v1}, \texttt{v2}, \texttt{v3}, \ldots
\end{itemize}
\end{frame}

\begin{frame}{Git: Record a Version}
\par\smallskip
\begingroup\centering
\begin{tikzpicture}[scale=.88,transform shape,node distance=10mm,font=\sffamily\small]
\node[gitbox] (w) {\textbf{Working folder}\\Files you are editing};
\node[gitbox,right=of w] (s) {\textbf{Staging area}\\Next snapshot};
\node[gitbox,right=of s] (h) {\textbf{Commit history}\\Saved snapshots};
\draw[gitarr] (w)--node[above=3mm]{\term{stage}}(s);
\draw[gitarr] (s)--node[above=3mm]{\term{commit}}(h);
\end{tikzpicture}
\par\endgroup\smallskip
\begin{itemize}
\item \textbf{Edit and save:} your working files change, but no new snapshot is recorded in Git yet.
\item \term{Stage}: choose which edits go into the next snapshot. Other tracked files retain their previously recorded content in that snapshot.
\item \term{Commit}: record the prepared snapshot in history, with your message. Later edits leave that snapshot unchanged.
\end{itemize}
\medskip
\courseexample{Case: Two files changed, only one is ready}\\
You edit \texttt{code.py} and \texttt{notes.txt}, but stage only \texttt{code.py}. The commit records the code changes; your unfinished edits to \texttt{notes.txt} stay in the working folder for later.
\end{frame}

\begin{frame}{Git: Branch and Merge}
\small
A \term{branch} lets you try an idea separately while a partner works on the main version.
\par\smallskip
\begingroup\centering
\begin{tikzpicture}[scale=.88,transform shape,font=\sffamily\small]
\node[gitcommit] (start) at (0,0) {Starting commit};
\node[gitcommit] (main) at (4.5,0) {Partner's edit};
\node[gitcommit] (combined) at (9,0) {Combined version};
\node[gitcommit] (try) at (3,-1.35) {Try an idea};
\node[gitcommit] (refine) at (6,-1.35) {Refine the idea};
\draw[gitarr] (start)--(main);
\draw[gitarr] (main)--(combined);
\draw[gitarr] (start.south) to[out=-90,in=180] node[gitlabel,below left]{\term{branch}} (try.west);
\draw[gitarr] (try)--(refine);
\draw[gitarr] (refine.east) to[out=0,in=-90] node[gitlabel,below right]{\term{merge}} (combined.south);
\node[gitlabel,above=2mm of main] {Main branch};
\node[gitlabel,below=2mm of try] {Your branch};
\end{tikzpicture}
\par\endgroup\smallskip
\begin{itemize}
\item Each box is a \term{commit}. Both branches start from the same history, then record separate changes.
\item \term{Merge}: bring the changes from your branch into the main branch.
\item A \term{conflict} means Git cannot combine edits automatically. Decide which content to keep, then complete the merge.
\end{itemize}
\end{frame}

\begin{frame}{Git: Push, Fetch, and Pull}
\small
Exchange commits with your partner through a shared repository.
\par\smallskip
\begingroup\centering
\begin{tikzpicture}[scale=.88,transform shape,node distance=10mm,font=\sffamily\small]
\node[gitbox] (shared) {Shared repository\\Online commits};
\node[gitbox,right=of shared] (downloaded) {Fetched commits\\Ready to inspect};
\node[gitbox,right=of downloaded] (current) {Your current branch\\Your working version};
\draw[gitarr] (shared)--node[above=3mm]{\term{fetch}}(downloaded);
\draw[gitarr] (downloaded)--node[below=3mm]{integrate}(current);
\draw[gitarr] (current.north) -- ++(0,.75) -| node[pos=.25,above]{\term{push}: send your commits} (shared.north);
\draw[gitarr] ([yshift=-3mm]shared.south) -- ++(0,-.45) -| ([yshift=-3mm]current.south);
\node[gitlabel,below=8mm of downloaded] {\term{pull} = fetch + integrate};
\end{tikzpicture}
\par\endgroup\smallskip
\begin{itemize}
\item \term{Push}: send your commits to the shared repository.
\item \term{Fetch}: download new commits to inspect. Your current branch and working files stay unchanged.
\item \term{Pull}: fetch and integrate updates into your current branch, using a merge or replaying your commits on top, depending on your settings. Resolve conflicts if needed.
\end{itemize}
\end{frame}

\begin{frame}{GitHub: Start from an Existing Project}
\term{GitHub} is an online platform for storing and sharing Git repositories. It gives a project a web address where you can browse its files and history.
\par\medskip
\begin{itemize}
\item Your \term{local repository} is on your computer. A repository hosted on GitHub can serve as the shared copy for a project.
\item A \term{remote} is a saved name and address for another repository. Git uses this connection when you push, fetch, or pull.
\item Read the project's \term{README}: the introductory file explaining what the project does and how to use it.
\item Run \term{git clone} with the repository's address to create a local folder with its files and history. Git also sets up a remote connection to the original repository.
\item Work in your copy, make commits, and fetch later updates. Pushing to the original repository requires permission from its owner.
\end{itemize}
\end{frame}

\begin{frame}{One Small Change, One Clear Commit}
\courseexample{Case: Improve the README}\par
\begin{enumerate}
\item Open the project folder in VS Code and inspect its Source Control panel.
\item Add a sentence explaining how to run the program.
\item Inspect the \term{diff}: the comparison between old and new content.
\item Follow the new instructions to check that they work.
\item Stage the intended files and commit with a useful message, such as ``Add instructions for running the program.''
\end{enumerate}
\medskip
Before committing, check that the diff contains only the changes you intended.
\end{frame}

\begin{frame}{Choose What Belongs in the Repository}
\small
\begin{tabularx}{\linewidth}{@{}YY@{}}
\toprule\textbf{Track and share} & \textbf{Keep outside the shared history}\\\midrule
Source code: \texttt{.py} and \texttt{.ipynb} & Local environment: \texttt{.venv/}\\
A README explaining how to run the work & Caches and notebook checkpoints\\
A list of required packages & Passwords, access tokens, and private data\\
Small, relevant results when requested & Large generated files that can be recreated\\\bottomrule
\end{tabularx}
\par\medskip
\begin{itemize}
\item A \term{.gitignore} file lists patterns for files Git should leave untracked.
\item Ignoring an already tracked file does not remove it from the repository or its history.
\item Check notebook outputs as well as code before pushing. A public repository makes its tracked content accessible to others.
\end{itemize}
\end{frame}

\begin{frame}{Connect Your Folder to GitHub}
\small
\begin{enumerate}
\item Install Git, register for GitHub, and open your project folder in VS Code.
\item In Source Control, initialize the folder as a Git repository. Set your commit name and email when prompted.
\item Add a README and a \texttt{.gitignore}; inspect, stage, and commit them.
\item Choose \textbf{Publish to GitHub}, sign in through the browser, choose a repository name and visibility, and check which files are included.
\item Open the resulting GitHub URL and confirm that your commit and files appear.
\end{enumerate}
\medskip
This workflow creates the GitHub repository and connects the local folder. If you already have a GitHub repository, clone it first and work in that local folder.
\end{frame}

\begin{frame}{Practice: Is the Change on GitHub Yet?}
\courseexample{Case: A Missing README Update}\par
You edit and save the README, make a local commit, and open GitHub. The website still shows the old README.
\begin{itemize}
\item Which steps have completed: save, stage, commit, push?
\item What would you check before trying again?
\item After pushing, where can you verify the commit message and changed file?
\end{itemize}
\medskip
Repeat with a second small edit. Explain the difference between the local history and the remote history to a partner.
\end{frame}
